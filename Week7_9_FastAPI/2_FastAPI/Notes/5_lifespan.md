
# FastAPI Lifespan and SQLAlchemy `refresh()` – Complete Notes

## 1. What is Lifespan?

Think about a real application.

When you start your server:

```bash
uvicorn main:app
```

Some things should happen **once** before the server starts accepting requests.

Examples:

* Create database tables
* Connect to Redis
* Load an ML model
* Initialize cache
* Start background workers

Similarly, when the server shuts down:

* Close database connections
* Close Redis connection
* Stop background workers
* Save logs

FastAPI provides **Lifespan** for this.

It is simply:

> **Code that runs once when the application starts and once when it stops.**

---

## Your code

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
```

This function has **two phases**.

### Startup

Everything before

```python
yield
```

runs **once**.

```python
async with engine.begin() as conn:
    await conn.run_sync(Base.metadata.create_all)
```

This creates all your database tables.

Then

```python
yield
```

means:

> "Startup is finished. Start serving HTTP requests."

Now FastAPI begins handling requests.

---

### Shutdown

Everything after

```python
yield
```

runs when the server stops.

```python
await engine.dispose()
```

This closes the database engine and its connection pool cleanly.

---

## Lifespan Timeline

```text
uvicorn main:app
        │
        ▼
FastAPI starts
        │
        ▼
lifespan()
        │
        ▼
Startup Code
(create tables)
        │
        ▼
yield
        │
        ▼

        │
        │
        │
Many requests...
        │
        ▼
Server shutdown (Ctrl+C)
        │
        ▼

(dispose engine)
        │
        ▼

```

---

## Why `@asynccontextmanager`?

A context manager has two parts:

```python
Before yield
```

and

```python
After yield
```

Exactly like

```python
with open("file.txt") as f:
    ...
```

Python automatically opens the file before entering the `with` block and closes it when leaving.

FastAPI uses the same idea for the entire application's lifetime.

# 2. What is `refresh()`?

This is another important SQLAlchemy concept.

Suppose you create a user.

```python
user = User(username="Ajay")

db.add(user)

await db.commit()
```

The database executes something like:

```sql
INSERT INTO users(username)
VALUES ('Ajay');
```

The database automatically generates values such as:

```text
id = 1
created_at = 2026-07-31
```

However, your Python object may not yet contain those database-generated values.

So you call:

```python
await db.refresh(user)
```

---

## What does `refresh()` do?

It tells SQLAlchemy:

> "Go to the database and reload this object's values."

Internally it performs a query similar to:

```sql
SELECT *
FROM users
WHERE id = 1;
```

Then it updates the Python object.

---

## Before and After `refresh()`

### Before

```text
Database
----------------
id = 1
username = Ajay
created_at = today

Python Object
-------------
id = ?
username = Ajay
created_at = ?
```

### After

```python
await db.refresh(user)
```

```text
Python Object
-------------
id = 1
username = Ajay
created_at = today
```

Now the Python object exactly matches the database row.

---

## Why do we need `refresh()`?

Consider this endpoint:

```python
@app.post("/users")
async def create_user(db: AsyncSession):

    user = User(username="Ajay")

    db.add(user)

    await db.commit()

    await db.refresh(user)

    return user
```

Without `refresh()`, the returned object may not contain values generated by the database, such as:

* Auto-increment IDs
* Created timestamps
* Default values
* Trigger-generated values

With `refresh()`, you return the latest version of the row from the database.

---

# `refresh()` vs `expire_on_commit`

Although they are related, they serve different purposes.

## `refresh()`

You explicitly tell SQLAlchemy:

> "Reload this object from the database **right now**."

```python
await db.refresh(user)
```

---

## `expire_on_commit=True`

SQLAlchemy automatically says:

> "After commit, mark this object as expired. The next time you access one of its attributes, reload it from the database."

This happens automatically.

---

## `expire_on_commit=False`

SQLAlchemy says:

> "After commit, keep using the values already stored in memory. Don't automatically reload them."

This is the common setting for FastAPI applications using `AsyncSession`.

---

# Mental Model

Think of your Python object as a **photocopy** of a database row.

* **`commit()`** → Save your changes to the database.
* **`refresh()`** → Throw away the old photocopy and make a new photocopy from the current database row.
* **`expire_on_commit=True`** → After saving, mark the photocopy as outdated so SQLAlchemy reloads it automatically when needed.
* **`expire_on_commit=False`** → Keep using the existing photocopy after saving until you explicitly choose to refresh it.

This explains why FastAPI examples commonly use:

```python
expire_on_commit=False
```

and still call:

```python
await db.refresh(user)
```

after creating a new record—the object stays valid in memory, while `refresh()` ensures it contains any values that the database generated during the insert.
